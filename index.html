⚠️ APIキー露出リスクAPI 金鑰外洩風險

SHOPLINEのScript EditorはフロントエンドのJSとして動作するため、Super8のAPIキーをそのままコードに書いてしまうとブラウザの開発者ツールで誰でも確認できる状態になります。APIキーが第三者に漏洩した場合、Super8 CRMのデータを不正に操作される可能性があります。 SHOPLINE 的 Script Editor 以前端 JS 運行，若直接將 Super8 的 API 金鑰寫入程式碼，任何人都能透過瀏覽器開發者工具查看。一旦 API 金鑰外洩，Super8 CRM 的資料可能遭到惡意操作。

❌ 危険な例（APIキーがフロントエンドに露出）❌ 危險範例（API 金鑰暴露於前端）
fetch('https://api.no8.io/tag', {
  headers: { 'Authorization': 'Bearer SECRET_KEY' }
})
🔍 まず確認：既存のプロキシサーバーがあるか首先確認：是否已有代理伺服器

SHOPLINEの購入データを自社DBに連携している場合、その仕組み次第でプロキシサーバーが既に存在する可能性があります。 若 SHOPLINE 的購買資料已連接至自有 DB，依其機制可能已存在代理伺服器。

✅ Webhookで受け取っている場合✅ 透過 Webhook 接收的情況

SHOPLINEのイベントを自社サーバーで受信しているなら、そのサーバーにプロキシ機能を追加するだけで対応可能。追加開発コストが小さい。 若自有伺服器已接收 SHOPLINE 事件，只需在該伺服器新增代理功能即可。追加開發成本較低。

⚠️ 手動・バッチ連携の場合⚠️ 手動或批次連接的情況

リアルタイムのサーバーが介在していないため、Vercel・Cloud Functionsなどのサーバーレスサービスでプロキシを別途構築する必要がある。 無即時伺服器介入，需另外透過 Vercel、Cloud Functions 等無伺服器服務建置代理。

1
最優先・今すぐ最優先・立即

社内IT / 開発ベンダーにIT1〜IT3を確認向內部 IT / 開發廠商確認 IT1～IT3

2
並行で実施同步進行

Super8サポートにQ1〜Q3を確認向 Super8 客服確認 Q1～Q3

3
回答後收到回覆後

パターン判定 → LP設置先・実装方式を確定判斷模式 → 確定 LP 設置位置與實作方式

4
設計フェーズ設計階段

タグ命名規則・フォローアップシナリオを設計設計標籤命名規則與追蹤推播情境
